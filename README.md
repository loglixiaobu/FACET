# FACET：按信息覆盖需求分配长文档检索入口

研究状态：2026-10-23。当前主线为 **FACET-Hybrid R＋C＋X**：真实块向量保底、最大剩余覆盖残差分配、入口数量校准、代表句轻量上下文化。

本仓库只发布核心算法、配置和小型调用示例；数据、模型权重、向量缓存、逐题预测和机器专用评测队列留在实验环境。现有结果是研究进展，核心假设尚未得到稳定验证。

## 1. 论文场景：什么问题、解决什么、核心claim

**问题场景。** 一篇长文档中，答案依据可能只是一句例外条件、一个数字、一段实体关系。整块只有一个embedding时，这些细节容易被大量常规描述稀释：依据实际位于块内，但块的整体语义与问题不够接近，检索阶段就会漏掉它。继续缩小块又可能破坏上下文、增加入口数量。

**要解决的问题。** 保留适合阅读的父块，为其中覆盖不足的细节增设句级检索入口。检索入口可以是句子，返回给回答模型的内容仍然是完整原文块。索引离线构建，只使用正文，不读取测试问题、答案或证据标注。

**核心claim（待验证）：在相同总向量预算、相同父块和阅读预算下，根据各块的信息覆盖需求自适应分配代表句向量，比均匀分配入口更能减少细节漏检，从而改善长文档问答。**

必须区分两个预算：

- 最终在线索引入口预算：`M = B + min(B, S)`，B为父块数，S为原句数；保留B个真实块向量，其余名额分配给句入口，通常为2B。
- 阅读证据预算：默认4096个Qwen token，包含拼接分隔符；与M分别控制。

M不限制全部离线编码量或缓存盘占用：当前方法仍需编码所有原句，X还可能产生额外编码。离线成本需要单独报告。固定块基线只有B个向量，因此它不能替代同预算Uniform对照。

## 2. 进度说明：基线、数据与已知结果

### 对比方法

| 方法 | 定义与比较作用 |
| --- | --- |
| Fixed128 | 严格128 Qwen-token固定块，每块一个向量，最终相似度顺序 |
| Rec128（此前称FC128/FC128_3sent） | 完整三句分组、128-token软目标，每块一个向量；分别评估原文/相似度顺序 |
| Uniform＋C＋X | 与FACET使用相同父块、真实块锚点和M，每块均匀分配句入口，控制C/X及最终顺序 |
| HiChunk | 历史HC200/HC200＋AM；新协议HC128/HC128＋AM，使用官方已SFT的Youtu-HiChunk，不自行微调 |
| LumberChunk（LC） | Qwen3-4B切块、BGE-M3检索、Qwen3-8B回答，保留原生段落策略及已记录的长段适配 |
| SemanticChunking（SC） | 本地SC基线：相邻原句BGE余弦距离第50百分位为断点阈值，再以128 Qwen-token硬上限打包 |

FC200是历史固定切块基线，不是HiChunk方法。FACET内部还测过覆盖收益分配G、相对校准C_rel、X空间选句及早期图模块，当前没有将它们全部并入主线。

### 当前结果与解释边界

六任务R/G×评分×表示八配置已完成8320项；Uniform及后续优化五配置完成5200项。以下是官方F1×100的任务等权均分：

| 六任务配置 | 均分 |
| --- | ---: |
| R＋C＋X | 42.4179 |
| Uniform＋C＋X（同向量预算） | 42.2634 |
| R_X＋C_rel＋X | 42.1601 |
| Uniform_X＋C_rel＋X | 42.3514 |
| Rec128原文顺序（仅B个向量） | 42.4255 |

主对照R＋C＋X−Uniform＋C＋X为 **+0.1545**，按源文档配对bootstrap的95%区间为 **[−0.2160,+0.5501]**；另外两组匹配R−Uniform对照的区间也跨零。目前不能认定自适应分配稳定优于Uniform。

四个LV任务×三方法×两个阅读预算的24组已完成3498项，官方逐题复算和完整审计通过：

| 阅读预算 | R＋C＋X | Fixed128相似度 | Rec128相似度 |
| ---: | ---: | ---: | ---: |
| 4096 | 52.20 | 46.07 | 51.56 |
| 8192 | 49.61 | 46.06 | 49.96 |

4096下RCX对Fixed128高6.13分，对Rec128高0.64分，后者95%区间跨零；扩大到8192没有平均收益。这是包含向量数、表示、评分和最终排序差异的系统比较，不能单独归因于自适应分配。

截至本次发布的进度快照，四LV任务上的Rec128原文顺序、HC128、HC128＋AM、LC、SC新一轮20组2915项仍在评估；Rec128已完成推理，整轮尚未全部审计，不发布其余方法的全量分数。早期夜间补测保留过一例已单独复核的并发缓存差异；新请求缓存使用完整请求身份与singleflight约束。分数表不是统一的新一轮全方法排名。

## 3. 算法流程与设计理由

```mermaid
flowchart LR
    A[原文与句界] --> B[三句分组 父块软128]
    B --> C[BGE块锚点与原句向量]
    C --> D[R 最大剩余残差分配]
    D --> E[X 已选句有限原文前缀]
    E --> F[块锚点 加句入口索引]
    F --> G[查询 C校准块评分]
    G --> H[完整块预算前缀 原文排序]
    H --> I[调用方Qwen3-8B回答]
```

1. **句界与父块。** 合并独立标题、编号、标点等碎片，完整三句成组，再按128个Qwen token软目标打包。完整组优先，允许超过128；极端超模型上限时显式拆分并记录。保留原文字符偏移，完整重建正文。这样使代表句有可选范围，并保留回答所需的局部上下文。
2. **真实块锚点。** BGE-M3编码真实父块及全部原句，使用归一化dense向量，实际实验为1024维。保留B个块向量，避免用某一句替代整块主语义；它同时是句入口覆盖和检索增益的参照。
3. **残差分配R。** 对每句计算其到本块锚点或已有代表句的最小平方欧氏距离。在全文选取残差最大的未选句，只更新所属块残差，直到额外名额用完；并列按原句ID稳定选择。信息重复的块可能少拿入口，覆盖不足的块可能多拿。Uniform沿同一局部最远点路径每块取一句，只改变跨块分配。
4. **轻量上下文化X。** 为已选句加入可靠原文标题及前一句片段：标题最多16 token，全部前缀最多64 token，目标句保持原样，再编码。目的在于补充指代、主语和局部语境；返回正文不改写。当前选句仍在原句空间，X只影响已选入口表示。
5. **数量校准C。** 令块锚点分数为a，该块句入口最高分为s，句增益`g=max(0,s−a)`；最终分数为`a+max(0,g−τ[语言,k])`，k为实际句入口数。多个入口的最大相似度天然可能偏高，C试图区分数量效应与有效增益。阈值来自独立训练背景的冻结95%分位校准；背景配对不是经认证的负例。稀疏k借用更大受支持k，超范围退回块分数。
6. **完整块检索与回答。** 按块分数取完整块排名前缀，遇首个超预算块停止，不跳过或截断；对实际最终顺序的拼接文本计token。FACET最终按原文顺序排列，再由调用方接入关闭thinking、贪心解码的Qwen3-8B。这样保留原文关系，但排序收益必须用独立对照检验。

模块对应：[分块](facet/chunking.py)、[R/G分配](facet/selection.py)、[X上下文化](facet/context.py)、[C评分](facet/scoring.py)、[完整块组装](facet/retrieval.py)、[组合接口与Uniform](facet/pipeline.py)。

## 4. 目前最大的难点

**最大的难点是：几何覆盖改善并不等于检索到了更有用的答案证据。** 最大残差可能优先分配给罕见但无关的句子、噪声或孤立表达。X空间的一组实验把覆盖残差改善约8.33%，问答均分却比匹配Uniform低0.1913分，说明当前代理目标与任务价值存在偏差。

另外，C可能抑制真实细节入口：原C下RCX与Uniform有76.25%的问题拿到相同上下文，预算分配变化没有充分传到回答阶段。原句选句与X空间检索也存在表示不一致。最后，分块、向量数、上下文排序及阅读预算都会影响问答，不能只凭优于某个系统基线就宣称核心claim成立。

## 5. 后续优化路线

以下是待检验路线，不是已经有效的模块；已有G、C_rel、X空间选句均未带来稳定整体突破。

1. **估计更有价值的剩余覆盖需求。** 在正文内部引入可解释的实体、数字、关系与稀有事实权重，结合覆盖残差和异常片段过滤，减少纯离群句占用预算。仍离线、查询无关，并与使用相同局部选句规则的Uniform匹配M。
2. **统一分配与检索的表示空间。** 优先检查哪些句子因X改变语义位置，尝试成本受控的候选上下文化或原句/X双空间一致性目标；同时报告额外编码成本，避免覆盖收益只是额外计算带来的。
3. **保留有效细节增益的校准。** 区分“入口多导致的偶然高分”和“明确补足证据的高分”，在独立背景数据上研究条件化校准；保持真实块锚点和受支持范围回退，不在测试答案上选阈值。
4. **建立证据与成本闭环。** 用QASPER/SciFact等真实证据标注定位漏检，单列细节型、多跳型问题，比较同M的Recall@K/覆盖率以及M/B变化曲线。切块、排序、评分、表示固定后再比较R与Uniform，并分开报告离线编码、最终索引体积、在线检索和生成成本。

## 6. 核心代码与调用

```text
facet/       分块、分配、上下文化、评分、检索及组合接口
configs/     当前协议、冻结context校准与基准任务设置
scripts/     单文档检索示例
tests/       无模型、无需GPU的核心回归检查
SOURCE_MAP.json  原始代码来源、SHA与提取改动说明
```

分配、上下文化、评分三个模块来自现有实现，保持原始内容；分块只替换Block类型的导入位置。组合层去掉了本机路径、旧输出目录和实验队列依赖。[配置](configs/default.yaml)记录BGE-M3、Qwen3-8B及预算；[冻结阈值](configs/calibration_context.json)仅适用于记录的语言、BGE及X表示，去掉X或更换表示时不能直接沿用。

```bash
python -m pip install -e .
python -m unittest discover -s tests

# 可选：需要自行准备模型及NLTK punkt_tab资源
python -m pip install -e '.[demo]'
python -m nltk.downloader punkt_tab
python scripts/retrieve.py --help
```

检索示例仅加载BGE模型及Qwen tokenizer，输出原文证据，不加载回答模型：

```bash
tmux new-session -s facet-demo \
  'CUDA_VISIBLE_DEVICES=0 python scripts/retrieve.py --document document.txt --query "问题" --embedding-model /path/to/bge-m3 --reader-model /path/to/Qwen3-8B --device cuda:0 > context.json'
```

正式对比默认仅使用GPU0、1、tmux、官方提示词和评分。FactRecall使用只输出人名的提示词及16-token回答上限，其余三个LV任务上限64；这些记录见[基准配置](configs/benchmarks.yaml)。完整基准驱动和第三方评分源码不在本精简仓库内，因此该示例不是一键复现所有历史分数的脚本。
